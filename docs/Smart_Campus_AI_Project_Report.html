Chapter 1: Introduction

1.1 Introduction of the Project

Smart Campus AI is a web-based student and campus services platform for J.C. Bose University of Science and Technology, YMCA. It brings academic planning, attendance, campus communication, events, reminders, and administrative workflows into one application. The system includes role-specific student, teacher, coordinator, administrator, hosteller, and warden experiences, with access enforced by the relevant application and server-side rules.

The application uses Next.js and React for its web interface and server routes, with Supabase providing authentication, PostgreSQL persistence, and real-time capabilities. Its AI assistant calls the Groq API and can ground campus answers in retrieved knowledge-base content through a Retrieval-Augmented Generation (RAG) pipeline. Supporting services include email delivery and campus mapping. The application is designed as a collection of connected workflows rather than as a standalone chatbot.

1.2 Problem Statement

Campus information and services are often spread across separate portals, messaging channels, and manual processes. Students may need to switch between systems to check attendance, track deadlines, find campus information, join events, or contact peers. Staff likewise handle repeated approval and communication tasks across distinct workflows.

A fragmented service landscape can make information harder to find and deadlines easier to miss. It also makes it difficult to connect campus information with a student's current schedule and role. A unified system is therefore needed to provide consistent access to academic and campus services, preserve appropriate role boundaries, and support routine tasks with automation and knowledge-grounded assistance.

1.3 Objectives of the Project

  1. Provide a centralized web platform for academic and campus workflows.
  2. Offer an AI assistant that can answer campus questions using retrieved knowledge when available.
  3. Help students organize schedules, reminders, and deadlines.
  4. Support attendance recording, reporting, and threshold alerts.
  5. Enable campus communication, notices, and a unified notification view.
  6. Support club and event discovery, registration, and attendance check-in.
  7. Provide hostel services, including access requests, maintenance, dining, and outpass workflows.
  8. Manage shared campus and hostel facility reservations with capacity controls.
  9. Enable lost-and-found posts and private item-claim communication.
  10. Apply role-aware access and data handling across student and staff workflows.

1.4 Learning from the Project

The project provided practical experience in full-stack web development, component-based user interfaces, API design, database modelling, user authentication, access control, and integration with external services. Building the application also involved managing persistent user state, designing validation rules for business workflows, and handling asynchronous communication with email, mapping, and AI services.

Implementing RAG provided experience with document chunking, text embeddings, vector similarity search, and source-aware responses. The project further required testing utility functions and workflow rules, maintaining database schema scripts, debugging integration issues, and coordinating a growing codebase using Git and GitHub.

Chapter 2: Literature Review / Related Work

2.1 Related Studies and Existing Systems

Learning-management systems such as Moodle and Google Classroom primarily support course delivery, learning materials, assignments, and classroom communication. Collaboration platforms such as Microsoft Teams provide messaging and meetings. Student information and enterprise systems manage institutional records and administrative processes. These categories of software address important parts of university operations, but they are generally configured around different service domains.

Standalone conversational assistants can answer questions but may not be connected to the actions a student needs to take, such as saving a reminder, viewing an event ticket, or tracking a hostel request. Conversely, conventional portals expose workflows but may require users to navigate separate sections and understand where information is maintained.

Smart Campus AI combines a dashboard with modular academic and campus workflows. Its distinguishing design goal is to place AI assistance, planning, communication, attendance, events, and selected administrative services in a shared application. The RAG feature can supply the assistant with retrieved institutional context and show source excerpts, while separate modules remain responsible for validated actions and persistent records. This integration is intended to improve discoverability and continuity; it does not replace the authoritative systems or staff decisions of the institution.

Chapter 3: Methodology

3.1 System / Model Architecture

Smart Campus AI follows a client-server architecture. The browser renders the application using React components within Next.js. Route handlers provide the backend-for-frontend API layer, validate and process requests, and communicate with Supabase or external services. Supabase stores relational application data and supplies authentication and real-time capabilities. The AI path adds an external language-model service and an optional retrieval path over campus knowledge.

The presentation layer contains dashboards and feature panels. The application layer applies role checks and domain rules such as attendance calculations, event registration validation, hostel assignment checks, and booking capacity. The data layer stores user state and domain records in PostgreSQL tables, with database policies and server-side access patterns used to protect data. The intelligence layer retrieves relevant knowledge chunks and uses the Groq chat-completion API to generate a response.

AI and retrieval flow

For eligible text queries, the server obtains an embedding using the Hugging Face Inference API and the sentence-transformers/all-MiniLM-L6-v2 model. The resulting 384-dimensional vector is compared with vectors stored in the knowledge_chunks table through a Supabase PostgreSQL RPC that uses pgvector. Retrieved chunks are formatted with source metadata and included in the system context sent to Groq. The response can include numbered sources and expandable excerpts in the interface. If the embedding service is unavailable or not configured, the AI route continues without retrieved context.

3.2 Data and Data Collection

The application does not train a machine-learning model on a single experimental dataset. It uses operational records entered by users or administrators and a separately managed knowledge base for retrieval. Data is stored in Supabase PostgreSQL tables and, for selected dashboard state, the per-user user_state store. Access to sensitive records is intended to be limited by authenticated identity, role, and database policy.

3.4 Algorithms and Techniques Implemented

  1. Retrieval-Augmented Generation: campus knowledge is chunked, embedded, and retrieved by vector similarity; relevant sourced passages are added to the AI prompt.
  2. Structured action detection: supported reminder, deadline, navigation, and club intents are parsed, validated, and confirmed by application logic.
  3. Role-based access control: dashboards and server routes enforce role and record scope, including block-scoped warden access.
  4. Attendance aggregation: records are grouped by student and subject to produce histories, percentages, and threshold indicators.
  5. Reminder scheduling: durable email jobs are processed server-side; browser notifications are best-effort.
  6. Capacity-aware booking: facility availability is generated from recurring schedules and validated against capacity and booking rules.
  7. Event check-in: registrations receive ticket identifiers for QR-based check-in, with validation intended to prevent repeat check-in for a registration.

Chapter 4: Implementation

4.1 System Design

The project is organized as a single Next.js repository with shared frontend components, API route handlers, server-side domain helpers, reusable campus utilities, and SQL schema scripts. The main dashboard serves as the entry point for student-facing functionality. Separate portal pages provide focused experiences for hostel and club workflows, while role panels expose teacher and administrator operations.

The code separates interface concerns from domain rules where practical. Components collect input and display results; route handlers authenticate requests and connect UI actions to server helpers; shared utilities validate inputs and calculate derived values. Database schemas define dedicated tables and policies for major areas such as chat, attendance, events, hostel services, facility bookings, and knowledge retrieval.

4.3 Workflows and Diagrams

Reminder and deadline workflow

A user creates a reminder or deadline in the dashboard. The application validates its details and persists the user's state. Scheduled email delivery is synchronized to a durable job record and processed by the reminder-job endpoint when a configured background trigger runs. Browser notifications can also be scheduled in the client but depend on browser permissions and availability.

Event registration and check-in workflow

A student views an event and registers during the permitted registration period. The event ticket is associated with that registration. On the event date, an authorized coordinator or administrator scans the ticket; the server checks the event and registration details before recording the attendance check-in.

Other representative workflows

  • Attendance: teacher records attendance → validated records are stored → student and staff views display subject-level histories and summaries.
  • Hostel maintenance: hosteller submits a request → assigned-block staff review and post updates → the requester tracks the request timeline.
  • Facility booking: an administrator publishes recurring availability → a student selects an eligible date and slot → the server checks capacity and access rules before confirming the reservation.
  • Lost and found: a student posts a found-item description → another student submits a private claim → claim communication remains separate from the public item listing.

4.4 Development Process (Frontend and Backend)

Frontend development

The frontend is built from React components rendered by Next.js. The main dashboard coordinates navigation and user state, while focused components implement planning, attendance, chat, events, hostel services, facility bookings, and lost-and-found interactions. Interfaces reflect the authenticated user's role and provide status, validation, and workflow feedback.

Backend and database development

Next.js route handlers provide application APIs for authentication, attendance, AI chat, events, hostel workflows, facility reservations, knowledge management, and reminder processing. Server-side helpers centralize domain-specific validation and service access. Supabase SQL files define the tables, indexes, functions, and access policies required by the feature areas; those scripts must be applied to the target Supabase project before the corresponding database-backed functionality is available.

Testing and development checks

The repository uses Node.js's built-in test runner for unit tests covering action parsing, RAG formatting, planner calculations, attendance summaries, issue workflows, inbox behavior, event check-in, facility booking validation, hostel services, lost-and-found rules, reminders, and role helpers. ESLint and the Next.js production build are provided as separate project scripts.

Chapter 5: Results and Discussion

5.1 Experimental Setup

Development and functional checks were performed in a Windows development environment using Node.js and npm. The application is intended to run in a modern web browser and can be started locally using the repository's development script. Backend-dependent workflows require valid Supabase configuration and, where applicable, configured AI, email, embedding, or mapping credentials.

The repository's automated checks use the Node.js test runner and project-specific utility and workflow tests. Manual testing should also verify complete user journeys in the browser, including authentication, role-specific access, API/database integration, notification behavior, and responsive layouts. No performance benchmark or production-scale load test is claimed in this report.

5.2 Evaluation Metrics

The project can be evaluated using the following measurable criteria:

  1. Functional correctness of each user workflow and its validation rules.
  2. Authorization correctness, including access to only the records permitted for each role.
  3. Attendance summary accuracy against known sample records.
  4. Reminder-job processing and delivery status under configured background scheduling.
  5. Event ticket validation and prevention of duplicate check-in.
  6. Facility booking capacity and eligibility enforcement.
  7. AI response relevance and whether displayed source excerpts support grounded answers.
  8. API error handling, reliability, and integration behavior with external services.
  9. Responsive usability and accessibility across supported browsers and screen sizes.

5.3 Results Analysis

The implemented application brings together a broad set of student and campus workflows: AI-assisted support, planning and reminders, attendance, chat and notices, events and clubs, hostel services, facility reservations, and lost-and-found. Dedicated route handlers, shared domain utilities, and database schema scripts provide the foundations for these connected features. The design supports role-specific flows rather than exposing every operation to every user.

An automated test run was performed for this report using npm test. It reported 69 tests: 68 passed and 1 failed. The failing test is buildStudentAttendanceReport groups course history and percentage. For its sample containing two present records and one absent record, the test expects an overall percentage of 66.7%, while the implementation returned 75%. This discrepancy remains an item to investigate; therefore, the current automated test run should not be represented as fully passing.

Chapter 6: Conclusion and Future Work

6.1 Conclusion

Smart Campus AI demonstrates how a modern web application can bring academic support and campus workflows together in one platform. Its combination of role-aware dashboards, persistent Supabase data, automation, real-time communication, and a knowledge-grounded AI assistant provides a foundation for a more discoverable digital campus experience.

Conversational assistance is kept distinct from authoritative actions: workflows are validated by dedicated services, while retrieved sources provide context for informational answers. Further testing, data governance, and deployment work are needed before institutional-scale use.

6.2 Limitations

  1. The application depends on Supabase and external AI, embedding, email, and mapping services for relevant features.
  2. RAG answer quality depends on the accuracy and freshness of indexed institutional content and on retrieval/model behavior.
  3. Browser notifications are best-effort and require browser permission; scheduled email delivery needs a configured background trigger.
  4. The automated test run currently has one failing attendance percentage test that requires investigation and resolution.
  5. Performance, accessibility, and scalability have not been established through formal benchmarks or production-scale testing.
  6. Institutional deployment requires administrators to configure environment secrets, database schemas, policies, and operational monitoring.

6.3 Future Scope

  1. Resolve the attendance percentage discrepancy and add edge-case tests.
  2. Expand end-to-end and authorization tests; evaluate AI grounding with campus questions, source checks, and user feedback.
  3. Improve monitoring and retries for reminder jobs and external services, and add push notifications.
  4. Explore indoor navigation and ERP integration; improve multilingual and accessible mobile use; conduct load, security, and deployment-readiness testing.
